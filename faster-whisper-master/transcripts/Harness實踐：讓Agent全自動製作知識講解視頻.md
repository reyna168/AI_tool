# Harness 實踐：讓 Agent 全自動製作知識講解視頻

## 前言

前段时间我發了幾條技術講解視頻，評論區好多同學問這些視頻效果是怎麼做的。正好趁著五一假期，我把整套視頻生成的流程封裝成了一個 Skill。今天就來跟大家完整地聊一下。

大家好，歡迎來到克諾米花園，我是歡迎老師。

今天這一期內容信息量很大，我們只要講三件事：

1. 我們的視頻到底是怎麼做的？
2. 背後的這個 Skill 是怎麼設計的？
3. 手把手帶大家走一遍完整的實戰流程——從一篇文章丟進去，到最後出來一個精美的知識講解視頻。

---

## 一、視頻製作方式：為什麼選網頁而不是視頻生成模型？

先跟大家交代清楚：效果**不是**用視頻生成模型做的，也沒有用 Runway 之類的工具。

其實它本身就是一個**網頁**，我自己用 Claude Code 寫出來的網頁。

### 為什麼不用視頻生成模型？

答案是兩個字：**可控**。

- 自己用代碼寫每一步的畫面，某一針要不要出現一個精確的數字，這些東西在代碼裡改一下就可以直接搞定
- 不用像視頻模型那樣抽卡，要穩定得多，成本也會更低

### 為什麼不用 No-Code 工具？

- No-Code 工具做不了動畫效果，出來的都是靜態圖
- Remotion 這種框架反而限制了模型發揮，有時候還不如直接讓模型寫要來得自由

### 演示案例

上期那個視頻就是完全由 AI 生成的，是我專門為做這期教程做的一個演示：

- **輸入**：Anthropic 最近發布的一篇文章
- **輸出**：一個網頁
  - 把原始文章拆成了 **13 個章節**、**100 多個細粒度的講解步驟**
  - 每一步都有完整的視覺演示效果
  - 底部有一個隱藏的進度條，鼠標滑到底部時會出現
  - 可以任意跳轉、切換到任意章節和步驟
  - 畫面裡沒有頁眉、頁眉，也沒有明顯的品牌標示，看起來就像一塊乾淨的畫面，更像視頻而不是網頁

## 二、做出好效果的四個關鍵要點

### 1. 文章 → 口播稿

原始的技術文章一般寫得都比較書面化，比如「該工具旨在提供高效的解決方案」，這種句子在視頻裡面是沒有辦法念出來的。

必須盡量把它改成**短句、口語化、第二人稱**的感覺，就像你在跟人聊天一樣。

### 2. 口播稿 → 開發計畫（大綱）

- 每一段話都對應一個具體的畫面步驟
- 每幾個步驟組成一個章節
- 每個章節聚焦一個話題
- 因為後續整個開發任務會非常複雜，提前做好這樣的大綱是保持後續穩定性的關鍵

### 3. 每步做視覺演示

這步非常重要，不是直接把口播稿上的文字放上去就完事了。我們得盡量讓網頁把抽象概念用**動態的效果**演示出來。

### 4. 畫面跟隨口播稿節奏

網頁的關鍵演示步驟一定是要跟隨口播稿的節奏去走的，這樣做出的視頻效果才能顯得非常自然。

## 三、Skill 設計：Harness 架構拆解

### 為什麼需要 Skill？

上面這些事情你也可以全部一步步地交給 Agent 去完成，也確實都能做出來——因為模型本身並不缺這些能力。

但問題來了：

- 怎麼讓它**每次都做得出來**？
- 怎麼讓不同的人、不同的文章、不同的主題都能**穩定地產出**？
- 怎麼讓開發效率**不靠運氣**？

直接跟 Agent 說「幫我做個視頻網頁」，它可能做得不錯，但也有可能會跑偏：

- 畫面對不上了
- 章節和音頻數不一致了
- 後面的章節風格突然跟前面完全不同了

模型是有能力的，但是你需要**一套機制**來駕馭這個過程。

> 這就是 **Harness 工程**需要負責的事情。

所以今天我們要講的這個 Skill，也是 Harness 的一個實踐案例。Skill 本身就是一份給 Agent 看的「操作手冊」，它告訴 Agent 什麼時候該做什麼、做到什麼標準。Agent 加載這個 Skill 之後就會按這些規則幹活，你不用每次都重新複述這些規矩。

### Skill 名稱

**Web Video Presentation Skill**，和其他 Skill 一起託管在 Garden Skill 倉庫裡面。

### Harness 的六個核心部分

一個成熟的 Harness 一般要包含 6 個部分：

1. **上下文管理**
2. **工具系統**
3. **執行編排**
4. **狀態和記憶**
5. **評估和觀測**
6. **約束和恢復**

---

### 3.1 執行編排：模型知道下一步該做什麼

整個 Skill 把「從一篇文章到視頻」拆成了**四個階段**，中間卡了**兩個人類檢查點**：

#### 階段 1：內容編寫

同時產出兩樣東西：

- **口播稿**：決定信息的描述方式和整體節奏
- **開發計畫**：決定每章做幾步、每步屏幕上放什麼內容

#### 人類檢查點 1

Agent 到這裡會被強制停下來，我們要確認：

- 口播稿和開發計畫還要不要改？
- 用哪套主題？
- 素材怎麼準備？
- 後續的章節開發是逐章做還是並行做？

#### 階段 2：章節開發

開發階段並不是一次性全部完成的：

1. 第一個章節開發完成後，**必須經過人類驗收**，確認視覺效果和節奏是不是都對上了
2. 它會為後續的章節開發提供一個基準參考
3. 後續的開發可以按順序做，也可以開多個 SubAgent 去並行寫
4. 每個章節完成後都要逐項對照檢查，直到全部過關才交付

#### 階段 3：音頻合成（可選）

章節開發完成後進入音頻的檢查點：

- 確認是不是需要自動合成音頻
- 如果需要 → 進入階段 3
- 如果不需要 → 直接跳到最後階段，用自己的聲音去錄製

音頻合成階段：

1. Agent 從口播稿對照網頁的步驟，提取出具體的音頻合成清單
2. 調用 TTS 的能力，把口播稿合成為音頻

#### 階段 4：錄製

- 瀏覽器打開網頁
- 開啟音頻的字幕播放
- 直接錄製就可以產出一個音頻和畫面天然對齊的成品視頻了

---

### 3.2 上下文管理：模型到底能看到什麼

這個 Skill 的流程橫跨了 4 個階段，涉及複雜的流程。如果行動的時候就把所有的文檔一股腦全灌進去，模型的注意力會被嚴重稀釋。

所以我們把所有的信息拆成了**多份文檔**，每一份文檔只在指定階段讀取：

| 文檔 | 讀取階段 |
|------|----------|
| 口播稿規範 | 第 1 階段 |
| 章節開發指引 | 開發階段 |
| 音頻合成文檔 | 音頻合成流程 |

**好處**：模型在任何時候，面前擺的都是它最需要的信息，不會被無關的內容干擾。

---

### 3.3 狀態和記憶：跨多個步驟保持連續性和穩定性

在這個 Skill 裡面，最重要的記憶就是**開發計畫**（Outline / MV）。

一個項目可能有十幾個章節、上百個步驟。Agent 寫到後面的章節時，前面定過什麼樣的結構、用戶在檢查點改過什麼樣的方向，很有可能已經不在當前上下文裡面了。

開發計畫的作用就是把這些關鍵的決定固定下來，成為開發階段的**持續記憶**。

#### 開發階段的三個核心文檔

在真正的開發階段，Skill 還會讓 Agent 強制去讀取兩個文件：

1. **口播稿**：負責整體的節奏，要先講什麼後講什麼，畫面一定要跟著口播稿去走
2. **原文**：負責信息的密度，因為口播稿通常會更精簡，畫面裡需要的數據案例可以從原文裡面去補
3. **開發計畫**：負責結構和步驟

三本文檔各有分工，Agent 開發每一個章節的時候都會從中去參考它們，就不容易出現：

- 結構對了但畫面空了
- 信息很多但結構亂了

> 這本質上也是一種**文件化的工作記憶**：把關鍵的狀態寫進這些文件，需要的時候再讀回來。

---

### 3.4 工具系統：模型到底能做什麼

這個 Skill 本身沒有用什麼特色工具，核心就是讓模型把自帶的文件讀寫工具用好就可以了。

#### 關鍵問題：多章節並行開發的衝突問題

在章節的開發流程中，它支持多章節並行的開發模式。多個 Agent 去同時改一個項目，會不會互相衝突？

Skill 設計了**嚴格的隔離機制**：

1. **物理隔離**：每章必須是獨立的文件夾
2. **CSS 前綴獨立**：每章是獨立的 CSS 前綴，不會互相起類名衝突
3. **全局變量控制視覺統一**：主題、顏色、間距都會走全局的變量，即使是每個 Agent 獨立開發，也能保持視覺風格的一致
4. **各章節互不影響**

---

### 3.5 約束和恢復：出錯了怎麼辦

在這個 Skill 裡面，出錯最常見的方式可能不是代碼報錯，而是**用戶覺得不對**：

- 這個章節節奏太快了
- 這個動畫效果太重了

面對這種反饋，Agent 的本能反應可能是**重做整個章節**——畢竟重新生成對 Agent 來說成本並不是很高。

但是重做整章的問題是：它會把已經做對的部分也改掉。比如某個步驟的節奏太快了，你直接重做了整章節，結果其他步驟原來很好的效果也變了，用戶可能反而更不滿意。

所以 Skill 裡面有一條**關鍵原則**：

> **反饋修復的最小切片**：問題在哪一層？是節奏、視覺、內容還是代碼？然後**只改最小切片**，不會重新做整章節。

---

### 3.6 評估和觀測：系統怎麼知道自己做得對不對

這塊花的心思是最多的，因為它直接對應一個核心問題：**自評失真的問題**。

讓寫代碼的 Agent 自己來評價「這章寫得怎麼樣」，這個結果大概率是「還不錯」。

所以我設計了一套非常硬性的自檢規則：

- 每個關鍵流程完成之後，**必須走自檢修復再匯報**的流程
- 每一個階段都有一套完整的自檢規則

最後的方案就是：

1. 用 **Claude Code** 開一個獨立的 Reviewer Agent
2. 給它產出文件加載的清單
3. 讓它從零開始逐項檢查

如果不用 Claude Code，也可以用 Cursor 等工具，最起碼都要：當前的 Agent 自己去逐項核查，但也要必須**嚴格逐項**，不允許目測一遍就放心。

---

### 小結

把 Skill 的設計攤開來看，你就會發現它和 OpenAI、Anthropic 的實踐本質上是沒有區別的，都是在搭建 Harness——只不過它們搭建的是工業級的運行系統，我們做的是 Skill 級別的協議。

> 做 Harness 不是非得從零去做一個 Agent。能用一個 Skill 約束 Agent 把一個垂直的工作做好，也是在做 Harness。

## 四、實戰環節

### 4.1 所需工具

| 工具 | 用途 |
|------|------|
| **Claude Code** | 核心執行 Agent（也可用 Cursor、Windsurf 等支持 Skill 的 Agent 工具） |
| **MiniMax** | 模型提供商，提供穩定的推理和生成能力，以及語音合成能力 |
| **CC Switch** | 桌面配置工具，讓 Claude Code / Cursor Code 等 Agent 切換為任意模型 |
| **tmux** | 終端管理器，可視化多 Agent 協作過程（可選） |

### 4.2 安裝 Claude Code

```bash
npm install -g @anthropic-ai/claude-code
```

安裝完後在終端輸入 `claude --version`，能顯示出版本號就說明安裝成功了。

> 國內正常使用 Claude Code 比較困難，目前推薦做法是搭配一個國產模型來用。

### 4.3 訂閱 MiniMax

MiniMax 的 Coding Plan 和 Claude Code 的配合非常好。

- 推薦訂閱 Plus 極速版，速度快、亮管夠、上下文非常高
- 日常的開發是完全夠用的
- 訂閱完成後會生成一個 API Key

#### 配置 CC Switch

1. 到 CC Switch 的 Release 頁面下載指定系統的安裝包
2. 安裝完成後打開它
3. 在 Agent 這裡選擇 Claude
4. 點擊加號，選擇內置的 MiniMax 提供商
5. 貼上剛剛在 MiniMax 生成的 API Key
6. 拉到最下面，其他都不改
7. 在主模型這裡全部都改成 `MiniMax-M1`
8. 點擊添加，然後點擊啟動
9. 打開終端啟動 Claude Code，確認模型已經切換到了 MiniMax
10. 嘗試對話測試，能正常輸出就說明配置成功了

### 4.4 配置 MiniMax CLI

MiniMax 的 Coding Plan 還有一個明顯的優勢：它附帶了多模態的套餐，包括圖片、語音、視頻，全部都是包含的。

在我們今天的教程裡面，有一個關鍵的節點就是要把口播稿合成音頻。MiniMax 的 Coding Plan 裡面自帶了每天 9000 字的語音合成額度，做兩篇文章是完全夠用的。

它的官方提供了一個 CLI，我們不用寫一行代碼，Agent 就可以直接調用完成語音的合成。

#### 安裝方法

```bash
# 在 Claude Code 中執行（將 API Key 替換為你自己的）
claude # 然後粘貼安裝指令
```

安裝完了之後，打開終端執行：

```bash
mmmx
```

如果能正常輸出信息，說明 CLI 就安裝成功了。

### 4.5 安裝 Skill

1. 訪問 GitHub 的倉庫地址
2. 拉到下面找到 `Web Video Presentation Skill`
3. 點擊下載安裝包
4. 下載完成後直接解壓
5. 得到 Skill 的具體目錄
6. 複製文件夾
7. 在編輯器打開項目目錄，創建 `.claude` 文件夾
8. 創建 `skills` 目錄
9. 把 Skill 粘貼進去
10. 在這個目錄下啟動 Claude Code

如果輸入 `/` 後能智能提示出 Skill，就說明配置成功了。

### 4.6 可選：Agent Teams + tmux

如果只是做一個小 Demo，一個 Claude Code 會話可能就夠了。但如果是做一個十幾章、100 多步的視頻項目，讓一個 Agent 從頭起到尾會非常慢。

Skill 在設計上對多章節做了嚴格的物理隔離，天然支持多 Agent 的並行開發。

#### Claude Code 的兩種多 Agent 能力

##### SubAgent（子代理）

像一個子進程：

- 主 Agent 把一個任務分出去
- 子 Agent 在自己完全獨立的上下文裡完成，然後再把結果交回來
- 各個子 Agent 之間互相看不到，也不會互相討論

適用場景：

- 並行開發多個章節
- 一次性檢查所有代碼
- 比較省 Token，也比較容易調度

##### Agent Teams（Agent 團隊）

像一個項目小組：

- 一個組長加上幾個組員
- 每個組員都是獨立的會話
- 之間可以互相發消息，也可以共享任務列表

適用場景：

- 需要來回反饋的任務（如測試員發現字太小 → 開發改大 → 測試再複查）
- SubAgent 做不了這種來回反饋，但 Agent Teams 就很合適
- 代價是 Token 消耗會更高一點（每個組員都是一個完整的會話）

> SubAgent 就像你讓三個人分別去三個城市辦不同事情，辦完之後回來匯報。
> Agent Teams 就像你把三個人拉進同一間會議室，讓他們邊討論邊改方案。

#### 啟用 Agent Teams

Agent Teams 目前還是一個實驗性功能。如果需要在 Claude Code 裡面啟用，需要在全局配置裡面加上環境變量：

```bash
export ANTHROPIC_USE_TEAMS=true
```

#### 安裝 tmux

tmux 是一個開源的終端管理器，可以在一個窗口中同時管理多個終端會話。配合 tmux 之後，Agent Teams 裡面每一個組員都會出現在不同的終端面板裡面，你可以同時看到測試員在哪裡、開發者在哪裡。

```bash
# 安裝 tmux
# macOS
brew install tmux
# Linux
sudo apt install tmux
```

在 Claude Code 的全局配置裡面加上 tmux 參數即可。

## 五、實戰演示

以《當你的一封郵件發出後的 600 毫秒》這篇文章為例，演示完整的視頻生成流程。

### Step 1：環境啟動

```bash
# 進入項目目錄
cd /path/to/project

# 啟動 tmux
tmux

# 啟動 Claude Code（危險模式，跳過所有工具調用確認）
claude --dangerously-skip-permissions
```

> ⚠️ 這裡加了 `--dangerously-skip-permissions` 是為了方便演示，實際使用時需注意安全。

### Step 2：生成口播稿和開發計畫

直接把原始文章丟給 Claude，告訴它使用 Web Video Skill 完成第一步。

Agent 會開始：

1. 用這篇文章編寫口播稿和開發計畫
2. 分別創建兩個審核 Agent 進行自檢
3. 自檢通過後，主 Agent 根據評審的結論進行更改
4. 輸出最終版本

#### 產出文件

| 文件 | 作用 |
|------|------|
| `script.md` | 基於原始文章改寫的、更適合視頻表達的口播腳本（句子更短、節奏更快、像真人聊天） |
| 開發大綱 | 把腳本和原始文章拆成細粒度的章節和步驟，標註每步屏幕上應該出現什麼信息 |

### Step 3：人類檢查點 1

Agent 會詢問幾個關鍵問題：

1. **稿子和開發計畫要不要改？**
   - 如果覺得稿子 AI 味比較重，可以手動調整成自己講話的風格
   - 確認規劃的大綱有沒有明顯的結構問題
   - 如果改了稿子，可以讓 AI 在下一步同時去調整開發計畫

2. **選什麼樣的主題？**
   - Skill 內部定義了幾套不同風格的主題
   - 會根據文本內容來推薦幾個主題
   - 也可以自己向它說明想要的風格

3. **素材怎麼準備？**
   - 後續生成的網頁中可能會用到一些圖片素材
   - 可以手動提供，也可以 AI 自己生成

4. **開發模式？** Skill 支持三種開發模式：
   - **模式 1（默認）**：需要逐章確認，每一章開發完成後都需要停下來人工驗收
   - **模式 2**：第一章開發完成後驗收，後續所有章節按順序做完
   - **模式 3**：第一章開發完成後驗收，後續所有章節用 SubAgent 並行開發

### Step 4：第一章開發與驗收

Skill 不會一上來就直接並行做完所有章節，而是會先做好第一章讓我們進行驗收。

因為第一章定下來之後，我們已經能看到整個項目的密度、動效的節奏、信息呈現的方式是不是合理了。如果跟預期差距比較大，我們還能及時調整。

> 第一章就是後續所有章節的基準。

打開它給出的地址，在瀏覽器直接驗收：

- 整個畫面是不是看起來很舒服
- 節奏是不是順暢
- 信息有沒有太密
- 有沒有明顯的 AI 味

如果有問題，發給 Agent 讓它繼續調整。如果沒有問題，就可以進入後續章節的開發了。

### Step 5：並行開發所有章節

啟用 Agent Teams，所有章節可以並行開發。經驗是**最多同時並行跑 3 個 Agent** 比較合適。

每個 Agent：

- 拿到自己負責的章節大綱、Skill 的規範、以及第一章的代碼作為參考
- 各寫各的，互不干擾
- 每章完成之後都會進入自檢環節

> ⚠️ 一定要選一個能力比較強的模型才能完成這樣的任務，不然多 Agent 的調度很容易出錯。

所有 Agent 開發並且自檢完成之後，才會向我們匯報任務完成。

### Step 6：整體檢查

所有章節開發完成後，整體檢查：

- 頁面上有沒有空白頁
- 動畫有沒有卡頓
- 位置對不對
- 有沒有內容的錯位

一共 50 多步的項目，中間某一步出現一些問題是很正常的。某一步如果覺得效果不太好，可以讓它重新改一下。

### Step 7：音頻合成

如果整體效果還不錯，就可以進入音頻合成階段。

1. Agent 會用配置好的 MiniMax CLI 把口播腳本批量合成為音頻文件
2. 合成之前，它會先從所有章節裡抽出一個詳細的口播文本清單（可以掃一遍有沒有措詞或漏句的情況）
3. 然後開始逐條合成音頻
4. 遇到速率限制等報錯，它會把出錯的文件記錄下來重新合成
5. 已經生成過的文件會自動跳過，中途中斷了也不用重來

合成完成後，在項目目錄裡可以看到音頻文件：每個章節有一個子目錄，每步都有對應的音頻文件，文件名和步驟編號是一對應的。

### Step 8：錄製視頻

Web Video 一共提供了三種錄製模式：

#### 模式 1：手動模式（默認）

不播放音頻，可以自己自由切換任意步驟，自己錄製自己的聲音。

#### 模式 2：音頻播放模式

在 URL 加上 `?audio=1` 參數：

- 每步會自動播放音頻
- 可以手動推進步驟

#### 模式 3：自動模式

在 URL 加上 `?audio=auto` 參數：

- 按下空格
- 頁面就會自動按照音頻的節奏去自動播放

大家自己選擇適合自己的方式去錄製就可以了。

## 六、總結

表面上看我們講的是一套「文章變成視頻」的流程，但是本質上它是一次 **Harness 的具體實踐**。

模型本身的能力已經很強了：

- Claude Code 能寫代碼
- MiniMax 提供穩定的推理和生成能力，以及語音合成的能力

但真正我們要關注的問題是：**怎麼樣把這些能力穩定地編排起來，讓 Agent 能夠穩定地完成？**

所以這個 Skill 做的事情，就是把一次複雜的內容生產任務，拆成有流程、有狀態、有檢查點、有自檢、有恢復機制的工程系統。

> 這也是 **Harness 最核心的價值**：把模型能力、工具能力和人的判斷，組織成一條穩定可控的生產流程。

大家也可以用類似的思路，在你的真實工作中實踐一下，希望可以給大家帶來一些啟發。
