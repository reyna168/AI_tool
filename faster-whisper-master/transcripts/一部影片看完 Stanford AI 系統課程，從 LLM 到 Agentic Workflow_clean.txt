那我們廢話不多說,直接開始,首先我們要先知道大型語言模型的限制是什麼,LLM要變強,有兩條路。
第一條是橫走,就是換更強的 Base Model,比方說從 GPT-4升級到 GPT-5,但橫走是 OpenAI跟 Antropic在做的,一般人沒有那個能力,
也沒有那個金錢去訓練自己的大型語言模型。
你能失利的地方是重走,也就是在現有的LLM上面疊各種工程技術,又叫做 Augmented in LLM,也就是想辦法提升這些 Base Model的能力,
而這整堂課,包括這支影片,講的都是重走的事情。
如果你只會使用 Base Model,在商業場景上一定會撞強。
舉個例子,CHGPT剛出來的時候,沒有聯網功能,沒辦法調用工具,衝擊量就是一個很聰明的問答機器人。
沒辦法實際幫你做完一件事,Stanford教授整理了 Base Model幾個常見的限制,第一次缺乏 Dolman knowledge。
比方說有一組學生在做自動化農業設備,要用相機判斷作物有沒有生病,這種農業病態的 Data Center是面上根本找不到。
換句話說,你的公司資料,內部文件,產品規格, Base Model都不知道,他也沒辦法根據這些資料幫你解決問題。
第二是資訊落後,模型不可能沒幾個月重訊一次,新詞,新事件,新公司,他通通不認識,年輕人在用的網路流行用語,模型大多也聽不懂。
第三個,控制很難,LLM是機率性輸出,同樣的 prompt 兩次跑可能結果不一樣。
在CHGP上聊天當然OK,但你想想production環境,使用者問退費,AI一下說可以,一下說不行,公司就麻煩了。
教授說,就連 OpenAI 跟 XAI 這種資金最多人才最期的團隊,都還沒辦法把LLM完全控制好,更何況一般公司。
第四個,當 Contacts 太長,模型的表現會顯出退步。
現在主流模型的 Contacts  window 已經拉到100萬Token,差不多是基本速的長度,但在這麼大的 Contacts 裡還是會出現 Lossing 的 middle 的現象。
簡單講,你把一個 Gary 5 餐吃了一顆蘋果這樣的小細節,常見公司過去一年的會議紀錄裡,
在問模型, Gary 5 餐吃了什麼,雖然這個狀況現在已經顯著改善,但 LLM 有時候還是會打不出來。
想做 AI 產品,光換更強的 base model 不夠,你需要再重走上實力。

那我們直接從 prompt engineering 開始講, Stanford 的教授說,他不認為 prompt engineering 會是一個職業,因為提示時工程,應該是每個工程時都該會的基本技能。
你不會靠 prompt  engineering 當飯吃,但這個技能會讓你在職壓利用一輩子,就像舊舊懲罰表一樣,是基本功。
我之前有做過一部影片專門再講 prompt engineering 有興趣的朋友可以去看看。
關於 prompt engineering 有一個很有意思的研究,我想分享給你。
頂級管理顧問公司 BCG 做過一個實驗,他們把一群顧問分成三組。
第一組沒有 AI,第二組可以使用 CHI GPT,第三組則是可以使用 CHI GPT以外,還有接受鑽寫提示詞的訓練,最後研究的結果發現三件事。
第一個叫 the jacket from tier,具詞編解,意思是 AI不是在所有任務上都表現得好,有些任務搭配 AI 顯著加分,但有些任務 AI 反而扯後腿。
第二個發現叫 Falling asleep at the wheel,翻成中文就是在方向盤前打顆碎,當你不知道任務剛好是 AI 不擅長的,卻太信任他把產出直接送出,結果比沒用 AI 還慘。
也就是說,你要知道 AI 的編解在哪,才不會在他弱的地方彩雷。
第三個現象最有趣,他們發現使用 AI 的方式分成兩種,分別是 Santos 跟 Cyborgs,
Center 是半人嘛,也就是分工違派型,丟一個常 prom 的給 AI 叫他做整份簡報,自己去做別的事。
Cyborgs 生化人是高頻來回型,跟模型一句一句對話協作, Stanford 的教授說,學生的使用習慣會比較像 Cyborg,
而企業在自動化 Workforce 比較像 Centaur,那你應該用哪一種?
關鍵詞看任務性質,重複性高,流程清楚的任務,用 Centaur 模式違派出去就好,
需要判斷,需要創意,需要來回校正的任務, Cyborg 模式才能逼出 AI 的最佳輸出,
兩者沒有好壞之分,實務上兩種都會用,重點是要有意識的切換。
接著進到實作,通常一個好 prom 的要有三個東西,給誰看,產出格式,重點是什麼?
請幫我總結,這邊文章是一個很爛的提示詞,因為什麼資訊都沒給。
但如果你寫的是,請將這份再生能源論文整理成五個重點在藥,
並且居交在其背後的政策意涵上,模型立刻知道對象是政策制定者,長度是五個點,
重點放在政策意涵上,你的產出品質會立刻提升。
但教授說, Prompt Engineering 里最常用最重要的一個技巧,不是這些,是 Prompt Chaining,
注意, Chaining 跟 Channel Thought 不一樣,
Chaining 則是把一個複雜的 prompt 採診多個獨立的 prompt 前一個的 output 位給下一個,
有用過 n8 的朋友應該知道在說什麼,舉個例,你要做客戶投訴回信,
單一 prompt 寫法是,讀這封投訴信,寫一封專業的回應,這就是一個黑盒子,
最後的產出如果有問題,你也不會知道該調整哪裡,
但如果使用 Prompt Chaining 採診三個 prompt,第一個抽出客戶在抱怨什麼,
第二個用抽出來的問題,起草大鋼,第三個用大鋼寫完整回信,
每一步都可以獨立測試,獨立 debug,
Chaining 不只讓模型表現更好,也讓你得到 observability,
能觀察 LLM 在做什麼,哪個流程出了問題,
講完 Prompt Engineering,下一個是 fine tuning,
Stanford 就要受對 fine tuning 的立場很簡單,能不做就不做,原因有四個,
第一,要大量的優質數據,如果你想要自己 fine tuning 模型,
就要有大量高品質的標註好的資料,
要做到這件事情的成本,對一般人來說,太高了,
第二個,容易 over fit,模型容易在你那個特定任務上變很強,
但通用問題反而打不出來,就會失去 basemodel 原本的廣度,
第三,實際上性差,這應該是最傷的點,
你花兩個月 fine tuning 完一個模型上線,
下個月新一代 basemodel 就出來,直接打給你 fine tuning 的版本,
第四,通常用 prompt engineering 也可以達到一樣的效果,
而且成本低很多,你想換新 basemodel 原本的 prompt 大多都是 parable的,
但 fine tuning 的模型不行,當然,針對少數情境 fine tuning 還是值得做的,
比方說法律、科學,那種需要重複高進度輸出的領域,
或者 basemodel 在某個都妹上表現吃力,這些情況下 fine tuning 都會有幫助,
但對大多數的人來說,其實不會有太大的效益,
所以,如果你想要把特定的 domain knowledge 塞進模型,
單純的提示詞工程,可能塞不下 fine tuning 的成本效益,又對不起來,
那時座端應該怎麼辦呢?
Stanford教授給出的答案是 RAC,
RAC 是 AI 工程師面試最常好的題目之一,
面試官常常會請你用五歲小孩聽著懂的方式,解釋什麼是 RAC,
你做 AI Build 也好,做 AI 工程師也好,這個是你一定要知道的事情,
RAC 節的碰點有幾個, Context Window 太小,長 Context 抓不準,
資訊有時效性,或者模型會產生幻覺, RAC 的做法很單純,
我用藥物副作用這個需要高度準確的醫療場景來說明,
通常 RAC 的做法是這樣的,先把所有的資料,文件,
用inbelly 模型把這些資訊轉成項量,
存進項量資料庫,英文叫做 Vector database,
所謂項量,就是把一段文字的語意轉換成一串數字,
語意相近的文字,轉出來的數字,正列在數學空間裡,距離也會比較近,
所以當使用者問藥物A 的副作用,我們不是在做關鍵字比對,
而是在找語意最接近的文件片段,
就算文件裡寫的是不良反應,而不是副作用,一樣能找到,
使用者的問題,也用同個inbelly模型轉成項量,
再用距離metric 從Vector database 裡找出最相近的Documents,
最後把這些Documents 加上 Citizen prompt 加上 user query,
組合成為給LOM 的最終 prompt.
Promptemplate 大概長這樣,根據以下Documents 回答使用者的問題,
如果Documents 裡沒有答案,就說我不知道,
這樣設計是為了把模型鎖在你提供的資料範圍內,
避免它自由發揮,平空捷走,
當然,你還可以要求模型回答時附上,
這個答案來自第幾頁,第幾章,第幾行,加超連結,
這樣使用者可以自行回述資料員進行驗證,
單純這樣做有時候不夠,
比方說,一種藥的相關文件可能租租有50頁,
整份直接轉成項量,
那很多細節疑失其中,
所以通常會搭配窗簾,
最基本的窗簾是把文件切成固定大小的片段,
每段各自轉成項量,
更進階做法是多層次存儲,
同時保留整片,每章,每段的項量,
Retrieval時可以先找到相關的章節,
再往下轉到進去的段落,
這樣在大文件裡的命中率會更高,
還有一個最近比較多人在討論的話題。
有人說,像現在已經有模型支援超長的Contacts window,
等這個技術成熟,算力夠便宜,
Basemodel直接讀完整個資料庫,Rap就沒用了。
但Stanford的教授認為這樣的說法,
理論上對食物上錯,
因為實際上你還是會遇到很多問題,
比方說Latincy,
你想想看每次問問題,
模型都要把整個Google Drive重讀一次,
沒人等得了。
就像搜尋引擎也是靠預先建好的所引,
來快速定位資料,
不可能每次Query都把整個網路重新爬過一遍,
所以Rag除了準確度以外,
還有檢鎖效率,可及時更新這類的優勢,
而這些優勢,
在可預見的未來都還是有其存在的價值。

先講下 Agente Workflow這個命令,
這個詞來自文達。
如果你不認識它,
文達是Corsairer的共同創辦人,
Google Brain 的創始負責人,
前百度首席科學家,
是在AI領域講話有一定份量的男人。
文達用 Agente Workflow這個詞,
是因為AI Agent已經被用到爛掉了。
有人寫了一個很長的 Pront,
叫 Agent,
有人做了複雜的 Multi-Agent系統,
也叫 Agent,
這個詞什麼都人套,
反而什麼都說不清楚。
所以它用 Agente Workflow
來精確描述一件事,
把一堆提示詞外部工具,
還有各種原件,
組合進一個有結構的工作流程裡,
成為一套系統,
這就叫做 Agente Workflow。
還記得我們前面講的 Rack 嗎?
Rack 主要做一件事,
給 LLN 外部資料當參考。
但 Agent 把 Rack 當作工具之一,
外加 Tool Cows, Memory,
都不做決策,
所以能做到 Rack 單獨做不到的事。
舉個例子,
使用者說,
我想推這筆訂單,
Rack 只能丟政策文件給你。
Agent 則是用 Rack Retrieve 政策,
主動問訂單 變號,
用拖查訂單,確認推廢。
告訴你,
三到五個工作廳會處理。
Rack 是工具,
Agent 是使用 Rack 這個工具的系統。
要打造 Agente Workflow,
你的工程性太要先翻轉過來,
因為傳統Sophia 跟 Agent AI Sophia
在四個面向都很不一樣。
首先是資料,
傳統軟體持結構化之料,
Jason 資料庫,
表單,
格式固定,
編界清楚。
Agentic 系統,
吃的是自由文本,
圖片,
英訊,
沒有固定格式。
第二個是邏輯,
傳統Sophia 是Deterministic,
同樣的Input,
永遠給你同樣的Output,
可預測,
可重現。
Agentic 系統是Fuzzy的,
意思是同樣的Input,
不同時間跑,
可能給你不同的Output,
因為 LAM 本身有隨機性,
加上它會根據 Context 做判斷,
沒有一個固定答案。
第三個是架構型態,
這個最重要。
傳統工程式的思維是寫 Micro Service 寫 Monolith,
你精確控制每一步執行路徑。
Agentic 系統的思維是 Finklike Manager,
你給 AI 個目標和限制,
讓它自己決定怎麼完成,
你管的是方向和邊界,
不是每一形成是馬。
第四個是測試,
傳統測試確定性的,
跑100次結果一樣。
Agentic 測試是迭代探索式的,
因為系統本身是非確定性的,
加上它對 Context非常敏感,
你沒辦法窮舉所有情況。
知道這世界是之後,
第一個落地原則就跟著來了,
能 Deterministic 解的問題,
就 Deterministic 解。
剩下發展的部分,加上互然。
加上舉自己的例子,
他們做Skills Assessment,
選擇題,配對題,Tolati,
用 Deterministic 算分,
因為這些有標準答案,
對就是對錯就是錯。
但語音題,
語音家Coding 的混合體型,
沒有標準答案,
沒辦法Deterministic 評分,
只能讓 ARM 去判斷。
這就是發記Scoring,
也就是沒有標準答案的評分。
你請 ARM 聽一段語音回答,
它要判斷這個人有沒有真的理解這個概念,
不要達是否清晰,
邏輯有沒有跑掉。
這些不是對或錯,
是一個程度的判斷。
ARM 會給你一個分數,
但這個分數是它覺得合理的答案,
不是算出來的。
發展的問題是它一定會犯錯,
ARM 可能誤判一個正確答案,
或是對模仁兩棵的回答給出偏低的分數。
在考試評分這種高風險的場景,
這不可接受,
所以他們設計了一個Apple Feature,
售測者可以對Agent 的判分提出申訴,
由真人介入審查並糾正。
這就是互然的具體形式,
不是試圖讓AI-0錯誤,
而是在它出錯的時候,有人介得住。
好,原則講完了。
要實際打造一個Agent,你需要哪些東西?叫做用定機票去巴黎當範例整理出三個核心藥署。
第一個是Prompt。前面講的提示池工程在Agent就是這一塊,你怎麼告訴AI他的角色是什麼,他能做什麼不能做什麼?
第二個是Contacts Management,也就是怎麼管理Agent在每一個當下看得到的資訊。
這包含幾件事,Memory,對話歷史,也可能有RackLaw回來的資料,通通都要塞進有線的ContactsWindow裡,
你要決定什麼重要,什麼可以丟,什麼要壓縮。
Contacts Management本質上只做一件事,那就是把對的資訊,在對的時間提供給你的Agent。
Memory本身有分兩層,Walking Memory是高頻要快的,比方說使用者的名字,這次的目的第一是巴黎。
Archival Memory是低頻可以賣一點的,比方說使用者過去五年的定房紀錄,需要的時候再去撈。
第三個是Tools,也就是Agent能呼叫的外部能力。
通常分成兩種,一種是作勢的,比方說FlySearch,Hotelbooking,Payment,一種是查資料的,比方說去CRM Loggo互資料,去資料庫查定單紀錄。
另外,課場上教授把Agent的資主性分為三層。
最低是HacoatedSteps,步驟全鞋死,先識別的用戶的意圖,在Lookup History,最後呼叫API,照順序走,安全,可預測,但很僵硬,遇到預期外的情況就卡住。
第二層是HotcodesTools,但讓Agent自己決定執行步驟。
你給他一組工具,告訴他你是TravelAgent,這些是你能用的工具,怎麼用你決定。
掌控工具範圍,但給Agent空間判斷怎麼組合。
這是目前最常見的Production Setup,也是教授推薦的起點。
第三層是FlyEthonomousAgent,自己決定步驟,甚至自己創工具,給他CodeEditor,給他WebSearch,讓他自己寫Code,解決問題。
能力最強,但風險也最高,你沒辦法完全預測他會做什麼,
如果Agent判斷錯誤,自己訂了100張機票,你就完蛋了。
還有一個關鍵概念是MCP,ModelContest Protocol。
傳統做法是你要替每一個API單獨寫串結邏輯,教LM這個API怎麼用,那個API要傳什麼參數。
MCP的做法是在中間放一個協議層,Agent不需要認識每一個API,他只需要跟MCP Server溝通,
MCP負責幫他跟後面的服務打交道。
你可以把MCP想成一個通用插頭,以前每個國家的插座規格不一樣,你要帶一堆轉接頭,有了MCP差一個就全通了。
Stanford教授還有提到對MCP一個更大的想像,那就是Agent to Agent Communication。
你可以把別人做好的Agent當做一種工具,讓你自己的Agent去呼叫他。
就像現在Agent呼叫API一樣,這是ModelAgent系統的基礎,我們等一下會講到。
不管是單一Agent還是ModelAgent,上線之前都要先回答同一個問題,怎麼知道他真的有用。
答案是Evelle,也是ProductionAgent系統的密碼。
教授在課長上給了一個完整的Evelle框架,是三個圍度交叉。
第一個圍度是N2N,還有Component-based.
N2N是看整體,使用者用完給幾分,滿不滿意,
Component-based拆開每一部款,比方說這個Tour老師忘記更新Email,送Email那一部格式不對。
觀看整體你找哪裡壞,但不知道為什麼壞,觀看Component你可能修了細節,但整體體驗還是差。
實物上兩個都要做。
第二個圍度是Objective,還有Subjective,也就是客觀和主觀的評價方式。
Objective是可以自動驗證的,使用者說All the IDs XLLM,寫進DB變成Y。
這種東西你可以寫個Python script自動對企,因為對就是對,錯就是錯。
Objective是沒有標準答案的,語氣好不好,回答夠不夠有同理心,這種要靠人工評分,或是用另一個額外的LLM當作評審,這個等等我會細講。
第三個圍度是Cortitative,還有Cortitative。
Cortitative是數字改地址,成功率,幾趴,每個環節的延遲多久。
Cortitative是感覺,在哪裡換覺,語氣哪裡不對,使用者哪一部卡住,這個要人工一筆一筆看,沒有接近。
剛剛提到的用LLM當作評審,又稱LLMS Judge,這是做Suppjective Evil常用的做法,設計上有四種主流玩法。
第一種是Paradise comparison,給George兩個答案,問他哪個比較好。
第二種是Single answer grading,直接打一到五分。
第三種是Reference Guided Paradise,多給一個標準答案做對比,讓評分更有依據。
第四種是RubricBased,你自己定義評分標準,比方說五分等於一百字以內,含三個重點,第一句是Overview,零分等於答非所問,容常識交。
這四種可以運用,比方說RabricBased,加上Futual Examples,讓評審更知道你要什麼。
怎麼實際跑一個Suppjective Evil,課堂上叫做用Travel Agent的禮貌度評估當例子,共拆成四個步驟。
第一步是Error Analysis,從一千個使用者裡抽二十個對話,人工讀。
你可能就會發現Error掌劃超短,有點機車,沒同理性。
這不不能省,你要先知道問題當什麼樣,才能設計出對的Evo。
第二步是設計Evo,用Error as Judge,加上自己寫的禮貌度Rubric,把你在第一步發現的問題翻譯成評分標準。
第三步是AB Test模型,固定Prompt把底層模型從GPD換成OPS或者其他模型,然後跑同一批對話, Judge 評分,看哪個模型禮貌度最高。
第四步是AB Test Prompt,固定模型,把 Act Like a Travel Agent,改成 Act Like a Helpful Travel Agent,看一個詞的差距影響了多大。
核心原則只有一個,先人工少出問題,再設計自動化Evo。
而且模型跟Prompt這兩個變形一次只動一個,不然不知道是哪個改動造成了差異。
講完Evo,叫做給了一個完整的case study,把前面所有東西串起來。
題目很簡單,我們要做一個克服AI Agent。
使用者可能會說,我要改A 127 訂單的地址,因為我搬家到建國南路了。
這樣的AI克服Agent,你會怎麼做?
這題目有兩層,表面看是怎麼改地址,本質是怎麼做一個會自己處理克服請求的Agent。
克唐上,一個學生回答說,我會先去克服旁邊做一到兩天,看他們實際怎麼處理這種請求,他們日常的工作流是什麼?
教授很喜歡這個答案,因為你要先理解人怎麼做這件事,才知道怎麼讓AI做。
而這就是做Agent Workforce 的第一步,叫做Task Decomposition,也就是把大任務拆解成小任務,讓LOM可以足夠擊迫。
觀察之後,你會發現,克服處理一個改地址請求,其實走了五步。
第一步,抽出關鍵資訊,包含克服的Intent是什麼?
O的ID是哪個,新地址是什麼?
第二步,去資料庫查克服紀錄,第三步,查公司政策,像是這筆訂單能不能改地址,是不是已經出貨了?
第四步,根據前面收集到的資訊,起草回信,第五步,送出Email,每一步都明確,這就是Task Decomposition。
有了拆解,下一步是決定每一步用什麼工具,第一步抽資訊,單純用LOM的一次API呼叫,通常就能解決。
第二步,喬汗改DataBase,要CustomTour或MCP Server。第三步,政策檢查,用REG,因為政策文件會更新,也需要有效率的減速,不能讓克服等太久。
第四步,根據前幾步,收集到的資訊,開始賺錢Email。
第五步,送Email,用Agent能夠使用的Email計算工具。
做這些判斷的方式很簡單,先問自己哪些步驟是發展,哪些是Deterministic,再決定每一步使用LOM,OneShot,REG,Tour,還是其他工具。
這就是AI Builder真實在做的工作,知道每個工具,每種技術的能力和限制,然後朝出一盤你需要的菜。
最後是BuildEvils,把前面講的三個圍度全部用上。
N2N看最終回覆正確性,語氣,使用者滿意度。
ComponentBase,拆開看每一步,抽資訊的準度,API錯誤率,政策專手率,
objective的部分可以自動驗證抽出來的OrderID是否正確,有沒有違反推廢政策。
subjective的部分要靠人工家LOMestge,比方說回信是否有禮貌,有沒有同理性。
Honitative,看改地址,成功率,Latincy,退費正確率。
Qualitative,看哪裡有幻覺,哪裡與氣步一致,使用者在哪一步感到困惑。
到這邊,一個完整的AI客服Agent從零到上線的工程流程就出來了,其實總共就是三個步驟,
先把大任務拆解成小任務,在設計工作流程,最後建立評估系統,確保產出穩定。
這堂課的最後一個主題是MotaiAgent,前面一個Agent已經人拆步驟,
Tort,做Rag,寫信,看起來夠用了,但MotaiAgent還是有它存在的理由。
主要原因是平行處理,有些是每理由排隊跑,定機票的時候,找航班,找飯店,茶天氣,這三件事,
完全可以同時進行,如果只有一個Agent,就只能一件一件做。
MotaiAgent就是把這幾件可以平行的是,拆給三個SpecializedAgent同時跑,速度直接拉起來。
次耀原因是Reusability,也就是可復用性,公司裡的DesignAgent可以給行銷團隊用,也可以給產品團隊用。
不過MotaiAgent聽起來很厲害,但做產品的時候要先問自己,真的有需要嗎?
如果一個Agent就能解決的任務,硬上MotaiAgent反而增加複雜度,
所以還是老化一句,工程設計能簡單就簡單,不要OverDesign。
票售用智慧家庭當Brandstone翻禮,一個完整的智慧家庭MotaiAgent系統可能有溫度控制,燈光,保全,娛樂,通知,還有能源管理,
這些Agent加上一個Ocastrate的統籌。互動模式有兩種,
第一種是Heroicical,使用者只跟Ocastrate講話,由他派工給下面的Agent,只會練清楚。
第二種是Fat,Agent之間,直接互通,沒有中間人。
教授建議智慧家庭以Heroicical為主,因為從使用者的角度,你不想同時跟五個Agent講話,
你只想跟一個System說我要出門了,他就會自己去協調燈光,保全,運孔。
但在後台,某些Agent之間可以有彼此之間水平溝通的連線方式,
比方說溫度控制的Agent跟能源管理的Agent之間互通,省掉每次都要過Ocastrate的溝通成本。
當你讓Agent之間互相溝通,本質上就是MCP Protocol。
你把Agent當作Tour,就跟把API當作Tour一樣。
這個心態一旦想通,設計就清楚了。
每個Agent對外暴露一組Tourlike見面,其他Agent像胡教工具一樣胡教這個Agent,
這樣子做結構乾淨,容易D-Bug,也支援平行處理。
MultiAgent聽起來複雜,但其實只是把你已經懂的東西,多疊一層。

第五層是Multi Agent,把每個Agent都當成工具,彼此協助來提升處理速度跟復用性。
